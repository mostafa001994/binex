# مرز اتصال Binix و n8n

## تصمیم محصول

Binix «مرکز معرفی، فروش و مدیریت» است؛ n8n «موتور اجرای سرویس» است. فروشنده هوشمند، رزرو، BI و تحلیل اکسل در نهایت داخل workflowها و کانال‌هایی مانند بله یا پیام‌رسان‌های دیگر اجرا می‌شوند.

## مالکیت مسئولیت‌ها

### Binix

- هویت کاربر و کسب‌وکار
- کاتالوگ، پلن، سفارش، پرداخت و اشتراک
- اتصال سرویس و نگهداری امن credential
- درخواست راه‌اندازی، وضعیت و تاریخچه عملیات
- اعلان، پشتیبانی، RBAC و Audit Log

### n8n

- اجرای workflow سرویس
- تعامل با APIهای بله و سایر کانال‌ها
- زمان‌بندی، پردازش و orchestration تخصصی
- گزارش نتیجه اجرای workflow به Binix طبق قرارداد

## وضعیت پیاده‌سازی

| بخش | وضعیت |
|---|---|
| مدل `AutomationConnector` | بنیاد آماده |
| رمزگذاری credential اتصال | عملیاتی |
| مدل `ProvisioningJob` و retry مدیریتی | بنیاد آماده |
| worker ارسال job به n8n | پیاده‌سازی‌نشده |
| callback/webhook امن از n8n | پیاده‌سازی‌نشده |
| idempotency سراسری | نیازمند تکمیل قرارداد |
| مانیتورینگ اجرای workflow | برنامه‌ریزی‌شده |

retry فعلی فقط job را دوباره در صف قرار می‌دهد؛ تا زمان وجود worker نباید به‌عنوان اجرای مجدد واقعی n8n معرفی شود.

## قرارداد پیشنهادی

این ساختار «پیشنهاد» است و قبل از پیاده‌سازی هر سرویس باید نسخه نهایی آن تصویب شود:

```json
{
  "contractVersion": "1",
  "jobId": "uuid",
  "idempotencyKey": "stable-key",
  "businessId": "uuid",
  "serviceId": "sales-agent",
  "subscriptionId": "uuid",
  "action": "provision",
  "payload": {}
}
```

پاسخ یا callback باید حداقل `jobId`، شناسه اجرای بیرونی، وضعیت، زمان و خطای پالایش‌شده را داشته باشد.

## الزامات اجرایی

- هر درخواست باید idempotent باشد تا retry باعث ایجاد سرویس تکراری نشود.
- secret فقط هنگام ارسال به مقصد مجاز decrypt شود و هرگز log نشود.
- endpoint باید allowlist، timeout و TLS داشته باشد.
- callback با امضا و محدودیت زمانی تأیید شود.
- retry دارای backoff، سقف تلاش و dead-letter state باشد.
- وضعیت اشتراک باید قبل از provision و در callback دوباره کنترل شود.
- خطای کاربرپسند و خطای فنی جدا نگهداری شوند.
